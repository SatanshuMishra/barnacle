# cb-rehearsal: CB rehearsals: drive the sign-up flow by hand in a throwaway server
Status: done
Updated: 2026-11-01T20:52:45.492Z

## Goal

Make the Clan Battle sign-up flow testable on the day a change is written. Every transition is wall-clock driven, so the soonest a developer can watch a post appear is the next CB night. A rehearsal server named in barnacle.toml gets two commands that exist nowhere else: one runs the real beat at a night's posting, closing or removal moment, and one deletes every Clan Battle season, post and answer the server holds.

- D4 The harness moves the clock and asks the beat, and never does the beat's work: Lift the weekday rule and give the harness one step verb. A rehearsal season is an ordinary season whose nights fall on every calendar day, which makes every night boundary a Wednesday-to-Thursday, so successive posting is exercised by construction rather than by special support. The harness owns no behaviour: it creates a season through the same store call, the same beat drives it, and its only knowledge of the timetable is next_moment, a function beside the beat that answers where the beat is going next and returns only instants strictly after now. A per-server clock offset, stored so a restart does not strand a rehearsal, is the only thing the step verb changes. That keeps the expansion contract simple: when the beat gains a transition, next_moment gains a row and the harness does not move, and a named test drives a season to exhaustion asserting the beat never acts at an instant next_moment did not offer. Compressing the schedule constants was refused because the owner fixed the CB times as given, and waiting on the real clock alone leaves the close, the handover and the cleanup untestable in a working session.

The supersedes entry on 01M2SJ24CHY840M99P4E914NWZ applies only to the rehearsal shape that decision replaced, not to the ping rule.

## Open risks

- R1 the_beat_skips_a_rehearsal_server (tests/attendance.rs:1063-1083) only covers the beat's post pass. The scheduled tick runs at lines 1067 and 1072, and at both moments the rehearsal season holds zero post rows (line 1071 asserts the post is None); the rehearsal post is only created by tick_in at line 1076, which is the last beat call. So the sweep pass (src/attendance.rs:272-298) and close pass (lines 299-324) are never exercised against a rehearsal season. Spec section 2 calls 'the background beat skips it entirely' the architecture, yet a regression that weakens the filter for close/remove, or a second scheduled path reaching beat or clear_posts without it, would close and delete a live rehearsal post mid-run with every test still green. Fix: after line 1078 add tick(FIRST_START) and tick(FIRST_REMOVE_AT), then assert state_of(elsewhere, first_night) == PostState::Open and board.deletes_in(REHEARSAL_CHANNEL).is_empty().
- R2 purge makes the season-management section 14.3 channel-drift window permanent. clear_posts (called at src/attendance.rs:236) aims every delete at season.channel, and vanished (src/discord/board.rs:110-117) maps both UNKNOWN_MESSAGE and UNKNOWN_CHANNEL to Removal::Gone. So a post whose real Discord message sits in the old channel after a raced /cb season move is counted as touched, marked Removed, and its row is then deleted by purge_season. Section 14.3's stated mitigation was 'the night self-heals at its removal time' - once the row is gone there is no row left to sweep, so the orphaned message is unreachable by any code path and only a human can delete it. Rehearsal-only, and spec section 13's owner check would surface it. Durable fix is the one 14.3 already names: store each post's own channel on its cb_posts row and delete against that.
- R3 The purge ordering rule is proven only for one season and a blanket delete failure. a_purge_whose_delete_fails_deletes_no_rows (tests/attendance.rs:1197-1249) sets up a single season with a single post. The partial case the rule exists for - season A clears cleanly, season B fails - is untested and cannot be constructed today, because FakeBoard::fail_deletes (tests/common/fakes.rs:274) is one global AtomicBool. That is the case where a future refactor is most likely to slip, for example moving the purge_season call inside the clear_posts loop, which would delete season A's rows before discovering season B's failure and would still pass the one-season test. Fix: add a per-channel delete-failure switch to FakeBoard, then a two-season test failing only the second, asserting PurgeReport { seasons: 0, messages: 1, answers: 0, failures: 1 } and both seasons, both post rows and all marks still readable.
- R4 A stale /rehearse registration survives decommissioning. register (src/discord.rs:176-187) only PUTs to guilds still in commands.guilds, and config validation (RehearsalNotRegistered) forces a retired rehearsal server to leave both lists at once, so its Discord command list is never rewritten. Flipping commands.scope to "global" has the same effect, since Discord keeps global and guild command sets separately. The entry stays routable because poise resolves slash commands by name against framework.options.commands with no guild check (poise-0.7.0/src/dispatch/slash.rs:73). The in-command guard refuses it so there is no data loss, but spec section 5's claim that the commands are 'absent' in a non-rehearsal server is false after any such config change, and an officer in a real clan server would see a live-looking /rehearse reset. Unconfirmed against a live install: confirming means dropping a guild from commands.guilds, restarting, and observing the command still lists.
